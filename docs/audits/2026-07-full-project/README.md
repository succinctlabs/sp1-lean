# Full-project audit — July 2026

This packet audits the whole `sp1-clean-native` repository, not only pull request #106. It covers the
architecture, Lean theorem strength, SP1 faithfulness, extraction provenance, use of Clean, proof debt,
and the semantic adequacy of AI-assisted proofs.

> **Frozen baseline, not current status.** This packet records the repository exactly at `6c399dbd` on
> Lean 4.30, before the consolidation/remediation work. Its findings and measurements are intentionally
> preserved rather than rewritten after the fact. As of the 2026-07-16 checkpoint, the project is on Lean
> 4.31; uses plain structural channels; has one 25/25 `advance` path and one supported-machine descriptor;
> deterministically decodes and rank-orders the active physical rows; globally grounds Program decode;
> and has begun exact typed Memory grounding with an Add chip contract. Whole-chip Rust oracles are landed
> for Add and Sub. The production capstone now stops at the named
> `supportedCore_orderedRows_dynamic` seam rather than claiming a balance trail is execution. The current
> audit passes with 460 probes and exactly 10 direct deferral sites in eight allowlisted files. See
> [`../../release-audit.md`](../../release-audit.md), [`../../architecture.md`](../../architecture.md), and
> [`../../proposals/consolidation-progress.md`](../../proposals/consolidation-progress.md).

## Executive verdict

The operation and chip layer is substantial and generally well engineered: the project has semantic
operation specifications, real Clean subcircuit composition, all 25 ordinary instruction chips are in a
single registry, all 25 now expose native Sail-facing `advance` relations, and most direct circuit proofs
are kernel checked without `sorry`. The branch's removal of the parallel `sailEquiv` path is a meaningful
architectural improvement.

The project does **not yet prove the advertised whole-machine claim**. The current ensemble theorem proves
the existence of a balance-derived state-key trail. Its constructor accepts per-row chip specifications but
does not use them, and `GatedExecution` contains no Sail-step property. The later target theorem contains a
real walk induction, but remains conditional on broad decode, readiness, entry, and target-obligation
hypotheses. This is a theorem-strength mismatch, not a Lean kernel failure.

The second central issue is provenance. Flat Rust constraint extraction reproduced exactly at the pinned
SP1 revision, but circuit and conformance regeneration did not. The updater exits successfully after
individual failures, eight registered circuit outputs differed, ten trace batteries and five witness
batteries could not be regenerated by the pinned Rust binary, and the checked-in Mul circuit is absent from
the circuit registry. In particular, the checked-in Bitwise circuit contains an extra booleanity constraint
not emitted by the pinned upstream implementation.

There is no evidence that completed proofs manufacture false proof terms: Lean checks them, explicit
axioms are absent, and the forbidden kernel-skip and main-library `native_decide` gates pass. The important
"AI cheating" risks are instead at the specification boundary: weak conclusions, ignored hypotheses,
vacuous semantic predicates for malformed prover data, semantic interaction interpreters that map most
buses to `True`, and theorem names/comments that claim more than their types establish. There are also 14
direct proof deferrals on this branch, including Mul completeness, DivRem soundness/completeness, and the
ensemble decode seam.

The right end state is close to the direction already described in the architecture-consolidation proposal:
an explicit, public-bound guest program; a non-vacuous boot invariant; per-chip `advance` lemmas; and a
production timed grounding engine deriving a single Sail execution from the actual bus multiset. Until that
engine exists, the balance theorem should be named and documented as a structural trail theorem rather than
machine soundness.

## Branch-specific assessment

The branch contributes several real improvements to the project-wide architecture:

- the Lean 4.30 migration is substantially complete;
- execution semantics were moved below the channel layer so contracts can reference them coherently;
- all 25 registered chips now expose one native `advance` relation;
- shared decode infrastructure was hoisted out of the old soundness layer;
- the duplicate `sailEquiv` / `reaches_sail` path was removed, leaving one intended transition contract;
- the State-channel experiment reached every chip, and the two-row grounding spike identified the need for
  frame/persistence facts.

The same branch also introduces or exposes the current merge blockers: Mul/DivRem proof deferrals under
4.30, dirty local dependency pins, a semantic channel contract without its production grounding engine, and
release documents that still describe the pre-cutover proof inventory. The PR draft is directionally useful
but should be regenerated from the artifact matrix before it becomes the release claim.

## Audit standard

Every claim in this packet is classified along three independent axes:

1. **Kernel status:** whether Lean accepted a complete proof term, and which axioms or deferrals it uses.
2. **Theorem adequacy:** whether the proposition actually expresses the intended SP1 or Sail property.
3. **Oracle provenance:** whether the modeled constraints, interactions, witnesses, and traces reproduce the
   declared upstream SP1 revision.

Passing one axis does not imply either of the others. This distinction is the central conclusion of the
audit.
